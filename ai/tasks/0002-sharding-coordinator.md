# Шардирование, координатор и node-адаптеры

## Проблема

Шардирование было декоративным: все узлы реплицировали один лог, «лидеры
шардов» назначались через gossip, координатор не маршрутизировал запросы,
gRPC и HTTP слушали один порт, пул соединений диалил собственный адрес.

## Требования

- Один Raft-груп на шард; узел — член ровно одного шарда.
- Координатор: `xxhash(key) % shards`, поиск лидера через `NodeService.Status`,
  кэш лидера, retry при смене лидера, HTTP/gRPC API.
- Node: gRPC `NodeService` (Raft RPC + клиентские Get/Put/Delete/Status),
  HTTP `/v1/kv/{key}`, health/status/metrics, Basic Auth, rate limit,
  graceful shutdown, репорт нагрузки координатору.
- Единый бинарь `db node|coordinator`.
- Интеграционный тест: 2 шарда × 3 реплики, маршрутизация, убийство лидера,
  сохранность подтверждённой записи.

## Критерии приёмки

- [ ] `go test -race ./...` зелёный, включая интеграционный тест.
- [ ] Координатор маршрутизирует ключ в правильный шард.
- [ ] После убийства лидера шарда запись не теряется, координатор повторяет запрос.
- [ ] `/v1/status` показывает карту шардов, лидеров и нагрузку.
- [ ] Не-лидер отвечает 503 + `X-Leader`, а не молча теряет запрос.
