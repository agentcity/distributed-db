# ADR 0003: range-based Multi-Raft и metadata service

- Статус: accepted
- Дата: 2026-11-16
- Контекст: M2 KV v2

## Контекст

v1: один Raft-груп на процесс, координатор с статической картой `hash % N`.
Это не даёт масштаба: нельзя держать много range на узле, нельзя split/merge,
нельзя перевозить реплики, нельзя быстро восстановить отстающую реплику.

## Решение

**Range-based Multi-Raft**:

- Ключевое пространство делится на диапазоны `[start,end)`; каждый range —
  отдельная Raft-группа со своим логом, лидером и snapshot.
- Узел — host многих групп (`internal/multiraft`); routing по `RangeID`.
- **Metadata service** (PD-like) хранит:
  - карту range → реплики → лидер;
  - версию карты;
  - TSO;
  - heartbeats и статистику для placement.
- Клиент кэширует `key → range → leader`; при not-leader обновляет карту.
- Split: range делится по ключу, обе половины получают новые ID и Raft-группы;
  старый range закрывается после передачи лидерства.
- Merge: соседние range с одинаковыми репликами объединяются.
- Snapshot: лидер отправляет `InstallSnapshot`, если `nextIndex` ниже
  компактированного лога.

Почему range, а не hash:

- range-скан и SQL-индексы требуют порядка;
- split/merge по размеру и нагрузке;
- локальность данных и предсказуемая маршрутизация;
- hash-шардирование оставляем как возможный режим для чистого KV.

## Альтернативы

| Вариант | Почему нет |
|---|---|
| Один Raft-груп на весь кластер | не масштабируется по логу и лидеру |
| Hash-шардирование | нет range-сканов, сложнее SQL-индексы, rebalance дороже |
| Статическая карта | не переживает рост/перекос, ручные операции |
| Отдельный coordination service (etcd) | лишняя зависимость; metadata можно реплицировать своим Raft |
| Shared log (Kafka-like) | другой класс системы, не даёт per-range лидера |

## Последствия

- Сложность: split/merge гоняются с лидерством и snapshot; нужна версия карты
  и идемпотентные операции.
- Нужен placement driver: балансировка по размеру/нагрузке, лимиты, anti-affinity
  по AZ.
- Клиент обязан уметь retry при смене лидера/range; без smart client будут
  лишние hop и ошибки.
- Snapshot/InstallSnapshot — обязательны до включения Multi-Raft, иначе
  отставшая реплика не догонит.
- Появляется отдельный control plane (meta), его нужно бэкапить и защищать.

## Проверка

- 3 узла, 2+ range; kill лидера range → новый лидер, данные живы.
- Split под нагрузкой; клиент видит новый range и не теряет ключи.
- Отстающая реплика догоняет через snapshot, лог не растёт бесконечно.
- Metadata service переживает рестарт и не выдаёт конфликтующие карты.
