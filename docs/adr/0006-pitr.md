# ADR 0006: Point-in-time recovery (PITR) and continuous backup

- Status: proposed
- Date: 2026-11-16
- Context: production gate G3 ([PRODUCTION-PLAN.md](../PRODUCTION-PLAN.md))
- Depends on: G1 durability (Raft fsync, snapshot/replay), G4 key management for encryption
- Related: [ADR 0002](0002-mvcc-percolator.md), [ADR 0003](0003-multiraft-ranges.md),
  [ARCHITECTURE.md](../ARCHITECTURE.md), [CONTRACTS-V2.md](../CONTRACTS-V2.md)
- Scope: architecture, formats, protocols and test/effort plan. No implementation
  code is part of this ADR.

## Decision summary

Adopt **periodic base snapshot + continuous Raft log archiving** as the PITR
mechanism. Do **not** build PITR on MVCC change-data-capture alone and do **not**
ship Pebble WAL/SST files.

- The **base** is the existing logical backup taken at a safe TSO `T_base`
  ([`internal/backup`](../../internal/backup)), extended to a paged manifest and
  object-store atomicity.
- The **continuous stream** is the committed prefix of every range's Raft log,
  shipped as immutable, checksummed, encrypted segments, plus the meta log/state
  (range map, TSO high-water, epoch).
- A **global checkpoint** records the newest TSO `T_safe` for which every
  range's archived prefix is complete and consistent, so a restore to any `T`
  in the retained window is well-defined.
- **Restore** materialises the base into a new, isolated cluster, replays
  archived commands with `T_base < commitTS <= T`, resolves cross-range locks,
  verifies the result, and only then cuts over with a higher cluster epoch.
- **RPO 0** is met only in `strict` acknowledgement mode: a commit is
  acknowledged after Raft quorum durability **and** the range archive
  checkpoint covers it. The default async mode has `RPO = archive lag` for a
  total-cluster loss and is explicitly not compliant with the stated RPO 0.
- **RTO < 30 min** is achievable at 1 TB only with a base interval of at most
  24 hours and at least ~2.5 GB/s aggregate restore throughput (or a shorter,
  incremental base); 24 h at 2 GB/s is borderline at p99. The math and the p99
  boundary are in §7.
- **Retention** is 7 days, enforced by dependency-aware GC over bases and log
  segments, never by object age alone.
- **Encryption** is client-side envelope encryption (AES-256-GCM, KMS-wrapped
  DEKs) plus TLS 1.3/mTLS; tenant isolation is not required initially.

This is a CP design: in strict mode, if the archive is unavailable, commits
fail rather than acknowledge data that a total-site restore could not recover.

## Context and current state

The current backup subsystem is a **logical, single-TSO backup**:

- [`internal/backup/backup.go`](../../internal/backup/backup.go#L33-L44) scans
  every range inside **one** `v2client.Txn`, so all chunks observe the same
  snapshot TSO; chunks are written to a staging directory and the directory is
  renamed only after the manifest and range-map recheck succeed
  ([`backup.go:119-143`](../../internal/backup/backup.go#L119-L143)).
- The manifest is a **flat** JSON list of every chunk
  ([`manifest.go:90-104`](../../internal/backup/manifest.go#L90-L104),
  [`manifest.go:192-236`](../../internal/backup/manifest.go#L192-L236)).
  Chunks are 1 MiB / 1000 keys by default
  ([`manifest.go:37-41`](../../internal/backup/manifest.go#L37-L41)).
- Restore verifies the whole backup, then writes **one transaction per chunk**
  ([`restore.go:221-241`](../../internal/backup/restore.go#L221-L241)). It does
  not delete keys absent from the backup and is explicitly not atomic or online
  ([`restore.go:137-145`](../../internal/backup/restore.go#L137-L145)).
- There is no continuous log/change archive, no restore-point tracking, no
  meta/TSO archive, no encryption, no retention GC, and no evidence for RPO/RTO.
  The CLI states this plainly ([`cmd/kvbackup/main.go:8-10`](../../cmd/kvbackup/main.go#L8-L10)).

Concrete gaps that this ADR must close:

| # | Gap | Evidence | Consequence for PITR |
|---|---|---|---|
| G-1 | RPO equals the backup interval | no log archive | all commits since the last full backup are lost |
| G-2 | Restore is not isolated or atomic | [`restore.go:137-145`](../../internal/backup/restore.go#L137-L145) | readers can observe a half-restored cluster; stale keys survive |
| G-3 | No global restore point | manifest has only one `SnapshotTS` | cannot say "restore to 12:34:56" or prove a point is safe |
| G-4 | Base scan can miss a commit at its own TSO | `mvcc.Scan` ignores locks ([`read.go:111-120`](../../internal/mvcc/read.go#L111-L120)); `Get` is the only path that returns `ErrLocked` ([`read.go:44-48`](../../internal/mvcc/read.go#L44-L48)) | a commit with `commitTS <= T_base` that resolves after the scan is absent from the base |
| G-5 | A commit may be allocated before it is applied | TSO is allocated in [`v2client`](../../internal/v2client/client.go) at commit time; there is no commit lease | an entry can commit after a base/segment boundary with an older `commitTS` |
| G-6 | Flat manifest does not scale to 1 TB | 1 TiB at 1 MiB chunks is ~1,048,576 descriptors | hundreds of MB of JSON, high restore memory and slow planning |
| G-7 | No archive of meta/TSO | meta Raft state is separate ([`metaserver/server.go`](../../internal/metaserver/server.go)) | range map and TSO high-water at `T` are unknown |
| G-8 | Range split/merge moves data outside the log | split copies records directly ([`kvserver/split.go`](../../internal/kvserver/split.go#L60-L78)) | raw-log replay alone cannot reconstruct a moved range |

The target is **G3**: PITR to any second in a 7-day window, restore into an
isolated cluster, RPO 0, RTO < 30 min, a monthly drill, and measurable evidence.

## 1. Requirements

### 1.1 Deployment and scope

| Item | Value |
|---|---|
| Product | private, single-tenant transactional KV + SQL |
| Topology | one region, 3 AZ, 3–5 nodes, 3 replicas per range |
| Dataset design point | 1 TB logical (tested), 1–10 TB target |
| Workload | OLTP, low-to-medium QPS, short transactions |
| Tenancy | one tenant per cluster; tenant isolation is **not** required initially |
| Object store | S3-compatible (S3 or MinIO), versioning and Object Lock preferred |
| Key management | KMS/HSM with envelope encryption |
| Retention | 7 days, any TSO in the window, not just daily restore points |

### 1.2 Functional requirements

| ID | Requirement |
|---|---|
| PITR-F1 | Restore the cluster to a caller-supplied **TSO** or wall-clock time `T`, producing the state at `T`: every committed version with `commitTS <= T`, no version with `commitTS > T`, and no unresolved transaction. |
| PITR-F2 | The restorable window is at least the last 7 days; any `T` in the window is addressable with TSO granularity (a TSO is at most 1 ms plus logical counter; see §1.4). |
| PITR-F3 | Restore **never** writes into a serving cluster. It targets a new, isolated cluster that accepts no client traffic until cutover. |
| PITR-F4 | Restore is **all-or-nothing at the cluster level**: before cutover the old cluster remains authoritative; after cutover the new cluster is authoritative; there is no dual-write state. |
| PITR-F5 | Cutover atomically fences the old cluster and all clients from the old incarnation, and prevents a stale client from writing to the restored cluster. |
| PITR-F6 | A restore can be interrupted and resumed from a verified checkpoint without exposing partial state; a second restore to the same target either resumes or is refused, never interleaves. |
| PITR-F7 | Every archived object is checksummed and its integrity is verified before it is referenced by a checkpoint and before it is used in a restore. |
| PITR-F8 | Base and log archives are encrypted at rest and in transit; restores require KMS authorization; keys can be rotated and destroyed (crypto-shred) at end of retention. |
| PITR-F9 | Range splits and merges during the backup window do not create gaps or duplicate data in a restore. |
| PITR-F10 | Cross-range 2PC transactions are restored atomically: a transaction committed at `commitTS <= T` is fully present; a transaction not committed at `T` is absent and its locks are rolled back. |
| PITR-F11 | Operators can list restorable points, inspect a restore plan, verify a backup set, and run a restore drill through a CLI/API; every action is audited. |
| PITR-F12 | Existing logical backups remain readable and restorable as full backups (non-PITR); the new format is versioned and forward/backward compatible per §4.9. |

| ID | Requirement | Target / measure |
|---|---|---|
| PITR-N1 | RPO | **0** for acknowledged commits in the failure model of §1.4; strict mode only (§7.1) |
| PITR-N2 | RTO | **< 30 min p99** from operator decision to serving traffic at 1 TB, 24 h base, ≥2.5 GB/s aggregate import, 10%/day change (§7.2) |
| PITR-N3 | Retention | 7 days; `restorable window >= 6.9 days` for 99.9% of the month |
| PITR-N4 | Consistency | no lost/partial transactions; no dangling locks; SQL catalog, rows and secondary indexes agree after restore |
| PITR-N5 | Durability | every acknowledged commit is archived; an archive outage must not silently degrade RPO |
| PITR-N6 | Operability | one-command plan/verify/restore; dashboards and alerts per §7.5–7.7; monthly drill |
| PITR-N7 | Security | TLS 1.3/mTLS for archive and restore; client-side encryption; KMS access audited; no plaintext keys |
| PITR-N8 | Tenant isolation | not required in v1; key hierarchy and object namespace are cluster-scoped so tenant-scoped keys can be added later |
| PITR-N9 | Compatibility | archive format v1 must be readable by all subsequent releases until deprecated; restore must refuse unknown critical fields rather than guess |
| PITR-N10 | Evidence | each drill emits a signed report with `T`, plan hash, object hashes, phase timings and RPO/RTO verdict |

### 1.4 Definitions and failure model

**TSO.** A timestamp is `physical_ms << 18 | logical`
([`internal/meta/tso.go:5-8`](../../internal/meta/tso.go#L5-L8)). It is allocated
only by the meta leader and is monotonic across leader changes because the
high-water mark is replicated
([`tso.go:17-60`](../../internal/meta/tso.go#L17-L60)). `T` in this ADR is a TSO
unless stated otherwise.

**State at `T`.** For every user key, the newest committed version with
`commitTS <= T`; deletes are tombstones; uncommitted locks are not visible.
Cross-range transactions are resolved per §3.8.

**Base and replay.** `T_base` is the TSO of a base snapshot. `base` is the
latest-state image at `T_base`, not a version history. Restore replays archived
commands with `T_base < commitTS <= T`; prewrites in an overlap window before
`T_base` are retained for transactions that commit after `T_base` (§3.5).

**Safe point and checkpoint.** `T_safe` is a TSO for which the archive is
provably complete and no future commit at or below it can appear. A persisted
**global checkpoint** publishes `T_safe`; a restore to `T <= checkpoint` is a
*safe restore*. `latest_recoverable` is the union of per-range complete
checkpoints after a total-cluster loss and is used for disaster recovery
(§7.1). These are not the same number; the distinction matters for RPO 0.

**RPO.** For every transaction whose commit was acknowledged to a client, the
recovery point contains that commit. RPO 0 is a property of the **recovery
point**, not of an arbitrary earlier `T`: restoring deliberately to a time
before a commit excludes that commit by definition.

**Failure model.**

| ID | Failure | In scope | RPO requirement |
|---|---|---|---|
| F1 | one node, disk, rack or AZ lost; quorum survives | yes | 0 |
| F2 | total loss of the primary cluster (all nodes/disks), object store survives | yes for RPO 0 strict mode | 0 in strict; `archive lag` in relaxed |
| F3 | object store loss or unrecoverable corruption | no (mitigated separately) | not guaranteed; optional second copy / Object Lock |
| F4 | operator error, bad migration, logical corruption, ransomware | yes | restore to before the event; 0 for the recovery point |
| F5 | region loss | no (single-region product) | not guaranteed; future cross-region copy |
| F6 | KMS unavailable | yes (operational) | restore blocked, no data loss; emergency escrow |

Assumptions: no Byzantine faults; object store is strongly consistent for
new objects (S3/MinIO today) and durable; KMS is available during restore;
NTP keeps clocks within a documented bound; Raft commit decision latency is
bounded by `Δ_raft_decision` (§3.5); the cluster has a hard maximum transaction
lifetime (§3.5). An entry undecided beyond the bound pauses base/safe-point
advancement until it is resolved; a retroactive commit beyond the bound is a
documented residual risk (F-21).

### 1.5 Non-goals

- Multi-region disaster recovery, cross-region active-active, or geo-PITR.
- Per-tenant backup/restore or tenant-scoped encryption keys (v1 is one tenant).
- Per-table or per-key restore (future: logical export/import on top of PITR).
- Backup of anything outside the KV keyspace (the SQL catalog, rows and
  indexes are inside the KV keyspace and are covered).
- Continuous audit logging of every read; only control-plane actions are audited.
- A guarantee for writes that were never acknowledged (client saw an error or
  unknown outcome); those are resolved by transaction retry/idempotency.

### 1.6 Acceptance criteria for G3

- [ ] `T` selected uniformly at random from the window restores byte-identical
      state for 1,000 trials, including deletes, cross-range transactions,
      splits, merges and rollbacks.
- [ ] kill -9 at every archive and restore phase leaves a resumable, verified
      state; no checkpoint references a missing or corrupt object.
- [ ] 1 TB dataset: p99 RTO < 30 min with the §7.2 configuration; the report
      states which phase dominated.
- [ ] strict mode: zero lost acknowledged commits after total-cluster loss in
      the kill matrix; relaxed mode is flagged non-compliant in the report.
- [ ] monthly drill passes; restorable window >= 6.9 days; encryption and key
      rotation verified.
- [ ] no plaintext backup data and no plaintext keys in the object store.

## 2. Design options

### 2.1 Option A — periodic base snapshot + continuous Raft/WAL archiving

**Mechanics.** A base at `T_base` is produced by the existing logical backup
(or, later, a physical range image). Independently, every range leader ships
its **committed** Raft log prefix to object storage as immutable segments.
Meta ships its log/state. A coordinator tracks per-range checkpoints and
publishes a global safe point. Restore loads the base, replays segments to `T`,
resolves locks and cuts over.

**Why it can meet RPO 0.** The Raft log is already fsynced before an entry is
acknowledged and is replicated to a quorum; it is the one durable source that
exists **before** the client sees success. Archiving it does not add a new
write path. With strict acknowledgement, the commit returns only after the
range's archive checkpoint covers the entry; with async acknowledgement, an
acknowledged entry is still on the quorum's disks but not yet in the object
store (RPO = archive lag for F2).

**Strengths.** No rewrite of the transaction/write path; per-range parallelism;
handles splits/merges through logical replay; reuses the tested base and
verification code; immutable log segments are cheap to checksum and encrypt;
the archive is append-only by construction.

**Costs.** A new archive agent, segment format, checkpoint/safe-point logic,
truncation gate and restore replayer; the archive includes prewrite payloads
(not only committed values), so it is larger than a pure change stream; the
base is a full scan and must be rate-limited; strict mode couples commit
latency/availability to the archive.

### 2.2 Option B — MVCC change archive / CDC

**Mechanics.** Capture committed changes as `(user key, commitTS, value/delete)`
records, from an apply-time hook or by scanning the write column
`w | userKey | be64(commitTS)`
([`internal/mvcc/mvcc.go:4-15`](../../internal/mvcc/mvcc.go#L4-L15)). Restore
writes the newest record per key up to `T`.

**Why it is attractive.** The smallest useful stream, layout-independent,
natural for logical replication and incremental bases; restore is trivial
compared with command replay.

**Why it cannot be the primary PITR source in this codebase.**

- The MVCC write column is indexed by `(key, commitTS)`, **not** by commit
  order. There is no global commit log; producing an ordered change stream
  requires either an apply-time hook (a new durable write before commit
  acknowledgement) or a full keyspace scan per interval (O(dataset), not
  O(changes)).
- A commit entry contains keys and `startTS`/`commitTS`, but **values live in
  the prewrite/lock record**; a commit-only record is not self-contained.
- For RPO 0, the CDC record must be durable before the client is acknowledged,
  which is a new synchronous write path and write amplification. Deriving CDC
  asynchronously from the Raft log is possible — but then the Raft log is the
  source of truth, i.e. Option A with a derived stream.
- Cross-range 2PC and rollback resolution still need the primary/lock state;
  a flat change stream hides locks and partial commits.

**Verdict.** Useful as a **future logical change feed** and as a way to build
incremental bases, but not the PITR source of truth.

### 2.3 Option C — storage-level snapshot + WAL

**Mechanics.** Take a Pebble checkpoint (hard links) per node and archive the
Pebble WAL; restore a compatible Pebble image and replay WAL.

**Why it is attractive.** Fast base (no logical scan), low CPU, exact physical
state.

**Why it fails here.**

- Storage is **shared per node** and range-scoped by a 10-byte prefix
  `'r' | rangeID | 0x00`
  ([`internal/kvserver/group.go:44-56`](../../internal/kvserver/group.go#L44-L56)),
  so one Pebble WAL/SST contains many ranges and non-range metadata. A
  node-local archive is not a cluster snapshot.
- Pebble WAL contains prewrite/provisional records and locks; without MVCC/TSO
  semantics it cannot answer "state at T".
- A cluster-consistent checkpoint requires coordinated checkpoints on every
  node plus every node's WAL, with no common TSO boundary; the archive becomes
  a set of node images whose mutual consistency is hard to prove.
- `internal/storage` exposes a read-only `Snapshot` and `Flush`, but not a
  Pebble `Checkpoint`; adding one pins a Pebble version/format for restore.
- Compaction/WAL recycling can delete data that is not yet archived; the
  failure mode is the same as log truncation but with less control.

**Verdict.** Rejected as the PITR mechanism. A physical range image may later
accelerate the **base** (behind the same logical checkpoint), but it is not the
continuous stream and not the restore-point authority.

### 2.4 Comparison

| Criterion | A: base + Raft log | B: MVCC CDC | C: Pebble snapshot + WAL |
|---|---|---|---|
| RPO 0 without new write path | **yes** (log already durable) | no (needs sync CDC) | no (node-local, no TSO) |
| Restore to arbitrary `T` | yes, with command filtering | easiest | only to a node image; no global `T` |
| Layout independence | yes (logical replay) | yes | no |
| Handles split/merge | yes (logical; lineage) | yes | very hard |
| Write-path impact | none for async; ack wait for strict | new hook + amplification | none, but storage-level coupling |
| Archive size | medium (includes prewrites) | smallest | largest (SSTs + WAL) |
| Restore speed | base + replay | fast | fastest base |
| Implementation risk | medium | medium-high | high |
| Reuses existing code | **yes** (base, verify) | partial | no |
| Meets the 1 TB / 7-day target | yes, with base interval tuning | yes, but sync cost | theoretically, not provable |
| **Verdict** | **recommended** | future change feed | rejected |

### 2.5 Decision and justification

Choose **Option A**.

1. It is the only option whose durability source already exists before the
   commit is acknowledged. RPO 0 therefore does not require a new synchronous
   write path in the transaction hot path for every deployment; strict mode
   only adds an archive acknowledgement, not a second data copy.
2. It preserves the existing, tested base/verify logic and keeps restore
   layout-independent, which is what makes split/merge and cross-range
   transactions tractable.
3. It has a clean failure boundary: the Raft log is the source of truth, the
   archive is an immutable projection, and the truncation gate is the only
   coupling between them.
4. B and C each move a hard problem (commit ordering, physical cross-node
   consistency) into the critical path without removing it.

Conditions attached to the decision (all are prerequisites, not optional):
commit lease/TSO safety (§3.5), truncation gate (§6), archive checkpoint after
RPO-critical durability (§7.1), restore fencing/epoch (§5.3), and paged base
manifest for 1 TB (§4).

Revisit if: (a) the product accepts RPO > 0 for total-cluster loss and needs
lowest commit latency; then async mode may be sufficient; (b) multi-region
logical replication becomes a goal — B is a better feed; (c) Pebble exposes a
portable checkpoint and the product accepts physical restore — C can be a base
accelerator, not a replacement.

## 3. What exactly is archived

### 3.1 Components

| Component | Runs on | Responsibility | Never does |
|---|---|---|---|
| PITR coordinator | meta leader or a dedicated control process | safe-point math, base scheduling, checkpoint publication, GC | serve client reads/writes |
| Archive agent | every KV node, one logical writer per range | tail committed log, seal/upload segments, write range checkpoints | archive uncommitted entries; truncate logs |
| Base builder | coordinator or a backup node | logical scan at `T_base`, paged manifest, upload | touch the live range logs |
| Meta archiver | meta leader | meta log/state, range-map changes, TSO high-water, epoch | archive KV data |
| Restore service | isolated target cluster | plan, materialise, replay, verify, cut over | write to the source cluster |
| Object store + KMS | external | immutable object durability, encryption keys | be trusted for ordering without checkpoints |

### 3.2 Archived data classes

| Class | Contents | Granularity | Source of truth | Included in restore |
|---|---|---|---|---|
| Base image | latest visible user KV at `T_base`, range map, counts, hashes | per range, paged chunks | live MVCC scan | yes, at `T_base` |
| Raft log segment | committed `model.Entry` records: index, term, type, payload | per range, contiguous index range | `raft.FileStore` / leader log | yes, filtered by `commitTS` |
| Meta log/state | range-map changes (with TSO), TSO high-water, incarnation/epoch, meta snapshots | meta Raft group | `metaserver` | yes, for map/TSO; not user data |
| Checkpoints/index | per-range and global safe points, segment hashes, lineage | per range + global | archive coordinator | consumed, not restored as data |
| Keys | KMS-wrapped DEKs and key ids | per archive set/segment | KMS | consumed |

**Explicitly not archived:** Pebble SSTs and Pebble WAL, in-memory Raft state,
locks as a separate object (derived from prewrites), TSO allocator internals
beyond the replicated high-water mark, and object-store lifecycle metadata.

### 3.3 Raft log segments

- **Committed only.** A segment contains entries with `Index <= commitIndex` at
  seal time. The uncommitted suffix is never archived: it can be truncated or
  replaced by a new leader
  ([`internal/raft/node.go`](../../internal/raft/node.go) truncates divergent
  suffixes), and archiving it would create a log that never existed as
  committed history.
- **Contiguous.** Entries `[start_index, end_index]` are contiguous with no
  gaps; the segment records `start_term`/`end_term` and the SHA-256 of the
  previous segment of the same range. A gap or a term regression is a hard
  error at restore.
- **Sealed.** A segment is sealed when it reaches a size/time boundary (target
  64 MiB, max 256 MiB, max 60 s) or when the range is frozen/split. Sealing
  freezes the byte stream; later entries go to the next segment. In strict-ack
  mode the sealer also seals **on demand** when a commit is waiting for an
  archive acknowledgement, so a low-traffic cluster does not add a full 60 s to
  commit latency; that on-demand segment is small and uploaded immediately.
- **Self-describing.** Header includes format/version, cluster id, incarnation,
  range id, index range, terms, first/last `commitTS` observed (not assumed
  monotonic), entry count, compression and encryption metadata; each record
  has a CRC32C; the footer has a SHA-256 and an optional signature.
- **Command payloads.** `model.Entry` types include `prewrite`, `commit`,
  `rollback`, `prewrite_commit`, `txn_batch`, `split_prepare`,
  `merge_prepare`, `noop`, and Raft membership entries
  ([`internal/model`](../../internal/model)). The restore parser must know
  every type; an unknown type is a **hard restore failure**, not a silent skip.
- **Writer identity.** Segments record the writer's range epoch/term. Two
  writers producing the same `(range_id, index range)` with different content
  is a split-brain alarm; the checkpoint rejects the lower epoch.

### 3.4 Base image

- A base is the existing logical backup: one MVCC snapshot TSO `T_base`, every
  range scanned in one transaction, per-range chunks, a manifest with bounds
  and SHA-256, and a range-map recheck before publication
  ([`backup.go:98-143`](../../internal/backup/backup.go#L98-L143)).
- It contains **latest visible values** at `T_base`, not MVCC history or locks.
  Values are imported at a reserved `base_ts = T_base` (no client transaction
  uses that TSO); committed replay writes at `commitTS > T_base` override them.
  A key absent from the base is absent at `T_base` (or deleted); a later
  commit may create it.
- Base exactness is **not** implied by the TSO alone. `mvcc.Scan` ignores locks
  and returns the previous committed value
  ([`read.go:111-120`](../../internal/mvcc/read.go#L111-L120)); a transaction
  that prewrote before `T_base` and commits after the scan with
  `commitTS <= T_base` would be missed. The base builder therefore needs a
  **base barrier**:
  1. choose `T_base <= now - Δ_safety` (§3.5);
  2. wait until every range's applied index covers its commit index
     (`lastApplied >= commitIndex`) **and** the commit index has been stable
     for `Δ_raft_decision`; a still-undecided entry means the base is retried,
     not published;
  3. wait until no range has a lock with `startTS <= T_base`; abandoned locks
     are resolved through the primary, not ignored;
  4. only then scan all ranges at `T_base`; if a lock or range-map change
     appears during the scan, abort and retry.
- The current `Backup` does not enforce this barrier; it must be added (or the
  base must be produced by a new `pitr base` mode that does). This is the most
  important correctness change hidden behind "we already have a consistent
  backup".

### 3.5 Consistency across ranges, meta and TSO

The archive is not a set of independent range backups: a restore point is a
single global TSO. Three mechanisms make that true.

**(a) Commit lease and bounded transaction lifetime.** A client receives a
`commitTS` and may hold it before proposing the commit. Without a bound, a
commit with `commitTS <= T` can appear arbitrarily late. The design requires:

- a **commit lease** `Δ_lease`: a commit RPC with a `commitTS` older than
  `now - Δ_lease` is rejected; the client retries and obtains a fresh
  `commitTS` (or the transaction is rolled back);
- a **maximum transaction lifetime** `Δ_txn_max`; locks older than this are
  resolved/aborted by the existing lock resolver (the default lock TTL is
  3000 ms; it must be configured consistently);
- a safety lag `Δ_safety >= Δ_lease + max_clock_skew + Δ_raft_decision`.
  A base or safe point never uses a TSO newer than `now - Δ_safety`.

`Δ_raft_decision` is the operational bound on Raft commit decision latency; it
is monitored and an alert fires when exceeded. This is the assumption that
converts "usually fast" into a testable property.

**(b) Per-range archive frontier.** For range `r`, at segment seal time, record:

- `A_r`: the applied index (entries applied by the state machine);
- `C_r`: the commit index (entries committed by Raft);
- `E_r`: the end index of the last complete segment;
- `L_r`: the minimum `startTS` of any lock record in the range, or `+∞`;
- `t_seal`: the TSO/clock at seal.

The segment is **complete** only if `E_r >= A_r` and `A_r >= C_r` (apply caught
up and everything applied is archived). Its **frontier** is

`F_r = min(L_r, t_seal - Δ_lease, t_seal - Δ_safety)`.

Why this is safe: a transaction that already has a lock has `startTS >= L_r`;
it can only commit at a `commitTS > startTS >= L_r`. A transaction without a
lock that starts later can only obtain a `commitTS > t_seal - Δ_lease` (lease)
and, more conservatively, `> t_seal - Δ_safety`. A 1PC commit (no lock) with an
older `commitTS` is either applied/archived by the barrier or rejected by the
lease. Thus no future commit at or below `F_r` can be missing from the archived
prefix.

**(c) Global checkpoint.** The coordinator publishes

`checkpoint_ts = min( min over ranges F_r, F_meta, T_base_of_latest_complete_base )`

and a generation/hash over the per-range checkpoints. A live source restore to
`T` is allowed only if `T <= checkpoint_ts`. `F_meta` is the meta archive
frontier (range map and TSO entries are applied/archived through the same
index). This is the number shown to operators as "latest restorable". A range
that has been created but has no complete segment yet contributes no frontier:
the global checkpoint **stalls** rather than assuming the range is empty. This
is the safe behavior for a newly split child.

**Base and logs together.** A restore to `T` needs a base with
`T_base <= T` and logs covering `(T_base, T]`. The base barrier ensures the
base equals state at `T_base`; the frontier ensures every commit in
`(T_base, T]` is archived; lock resolution (below) ensures partial 2PC
transactions are completed or rolled back consistently.

**TSO after restore.** The restored meta must start with
`LastTS = max(T, max commitTS present in the restored state, archived meta
LastTS) + margin`, with `LastPhysical`/`LastLogical` derived consistently
([`internal/meta/state.go`](../../internal/meta/state.go)). If the target
clock is behind, `AllocTS` still moves forward from `LastTS`
([`tso.go:28-60`](../../internal/meta/tso.go#L28-L60)). Starting below a
restored `commitTS` would make new writes invisible to snapshot reads; the
verify phase rejects it.

### 3.6 Finding the global restore point from a wall-clock request

- The operator supplies either a TSO or a wall-clock instant.
- For a wall-clock instant, map it to the largest TSO whose physical part is
  `<= floor(unix_ms)`: `T = (unix_ms << 18) | (2^18 - 1)`, then clamp to
  `checkpoint_ts` and `oldest_restorable_ts`.
- Because the TSO physical part is the meta leader's clock, clock skew shifts
  the mapping; the API returns both the requested wall time and the chosen TSO
  and warns if the two differ by more than `max_clock_skew`. Restores are
  expressed in TSO in the plan/report; wall time is only a UI convenience.
- A wall-clock second is not an exact boundary: a TSO is one logical point.
  The chosen `T` includes all commits with `commitTS <= T`; a commit at
  `T + 1` is excluded. The plan prints the first excluded `commitTS` and the
  first included one, so the operator can verify the boundary.
- Never silently round up: rounding up can include a destructive transaction
  (e.g. `DROP TABLE`). The default is floor; a `--round=up` flag exists but is
  audited.

### 3.7 Cross-range 2PC and lock resolution at `T`

A restore that simply rolls back all remaining locks is **wrong** for
Percolator-style 2PC: a transaction may have committed its primary range and
crashed before committing a secondary. Its secondary lock must be **committed**
at the primary's `commitTS`, not rolled back.

After replay and before verify, scan the target's lock records:

| Case at `T` | Decision |
|---|---|
| lock with primary write/delete at `commitTS c <= T` | commit every lock of that `startTS` at `c`, using the staged prewrite value; remove locks |
| rollback record for `startTS` | roll back the lock; remove it |
| primary lock still present, no commit at `c <= T` | at snapshot `T` the transaction is not committed: roll back at `startTS` |
| primary lock present with `commitTS > T` (not yet committed at `T`) | roll back at `startTS`; the transaction is outside the snapshot |
| orphan lock (primary key absent in the restored state) | roll back; log as an anomaly and fail verification if not explainable |

The resolver is idempotent, processes primaries before secondaries, and records
counts (`resolved_committed`, `resolved_rolled_back`, `orphan`). A non-zero
orphan count is a failed restore unless the archived log proves the primary
never existed (then it is data corruption).

**Staged prewrites are resolved too.** A prewrite in the `T_base` overlap that
did not become a target lock still carries `(startTS, key, value, primary)`.
After replay, for every staged entry:

| Case at `T` | Decision |
|---|---|
| primary write/delete at `commitTS c <= T` | materialise the lock at `startTS` and commit the key at `c`; count `resolved_committed` |
| primary rollback at `startTS` | discard the stage; count `resolved_rolled_back` |
| primary exists but has no commit at `c <= T` | discard the stage; the transaction is not committed at `T` |
| primary absent and no rollback/commit record | orphan: fail the restore unless the archive proves a rollback |

This is how a **partial cross-range commit whose secondary commit command was
never archived** is recovered: the primary commit is replayed, the secondary
prewrite is staged from the overlap, and staged resolution commits the secondary
at `c`. Without this step the secondary key would silently keep its old value.


This resolution is also what makes a **partial commit at the source** safe: the
secondary commit command may be missing from the archive (it was never sent or
not applied), but the secondary prewrite is archived; the primary's commit
record decides the outcome. This is exactly the source cluster's own recovery
rule and must be reproduced, not approximated.

The resolver does not see locks for transactions committed at or below
`T_base`: replay deliberately does not re-create them (see §5.5), so a base
value is never mistaken for a missing primary commit. Staged overlap prewrites
are resolved against the primary by the table above, not by assuming they are
locks.

### 3.8 Range split and merge

- Split copies records directly from the parent to the new group
  ([`kvserver/split.go:60-78`](../../internal/kvserver/split.go#L60-L78)) and
  deletes the right side from the parent. This data movement is **not** a
  sequence of user-key commits in the Raft log, so raw replay cannot reproduce
  it.
- It does not need to: if the split happened before `T_base`, the base contains
  the data under the new range id; if it happened after `T_base`, the parent
  base already contains the key and the child's subsequent commits replay. The
  only dangerous case is a split **during** the base scan; the existing range
  map recheck aborts the base
  ([`backup.go:119-131`](../../internal/backup/backup.go#L119-L131)). The PITR
  base builder either freezes splits for the scan or retries.
- The archive must **follow new ranges** immediately: a child starts with an
  empty Raft log (index 1), and its segment stream begins there. The
  coordinator registers lineage `{parent_id, split_key, children}` from the
  meta archive; if a new range is not registered before its log would be
  truncated, the truncation gate blocks and pages (no silent gap).
- A merge seals the predecessor ranges and creates/continues the merged range;
  lineage records predecessors before the successor.
- Replay order is **lineage order**: predecessors before successors, each range
  in Raft-index order. This preserves per-key history when a key moves between
  ranges. If lineage is missing (meta archive gap), the replayer falls back to
  a two-pass staged replay or refuses; it never guesses an order.
- The restored target does not have to use the historical range map. Replay is
  logical (by user key), so the target map can be the archived map at `T` or a
  fresh contiguous map (§5.4). Data correctness does not depend on the source
  boundaries.

### 3.9 Why not archive MVCC commit records or Pebble SSTs

| Question | Raft log segment | MVCC commit record | Pebble SST |
|---|---|---|---|
| Durable before ack? | yes (quorum fsync) | no, unless a new sync path | yes on the node, but not cluster-wide |
| Commit-ordered? | per range, index-ordered | per key, not globally ordered | physical order, no commit semantics |
| Self-contained values? | yes (prewrite payload) | yes only if built at apply time | yes, but includes all internal records |
| Handles split/merge? | yes, with lineage | yes | no |
| Cross-node consistent point? | yes via TSO/checkpoint | yes via checkpoint | no |
| Restore cost | base + replay | base + small replay | image + WAL |
| Verdict | **archive this** | future feed | no |

## 4. Backup manifest, index, checksums, encryption, retention, upload

### 4.1 Object namespace

All keys are prefixed by cluster id and incarnation so two cluster lifetimes
never mix:

| Prefix | Object | Mutable | Notes |
|---|---|---|---|
| `c/<cluster_id>/<incarnation>/timeline/current.json` | timeline pointer | atomic replace | generation + signature |
| `.../timeline/<generation>.json` | immutable timeline | no | previous hash, bases, checkpoints |
| `.../bases/<base_id>/manifest.json` | base manifest | no | paged chunk index |
| `.../bases/<base_id>/pages/<page_id>.json` | chunk-index page | no | bounded descriptors |
| `.../bases/<base_id>/ranges/<range_id>.json` | range base descriptor | no | bounds, counts, hashes |
| `.../logs/<range_id>/<start>-<end>/data.bin` | log segment | no | sealed |
| `.../logs/<range_id>/<start>-<end>/meta.json` | segment metadata | no | hashes, terms, frontier inputs |
| `.../logs/<range_id>/checkpoint/<generation>.json` | range checkpoint | no | frontier, archived index, lineage |
| `.../meta/log/<start>-<end>/data.bin` | meta log segment | no | range-map/TSO/epoch |
| `.../meta/state/<generation>.json` | meta state snapshot | no | range map, TSO high-water |
| `.../checkpoints/<generation>.json` | global checkpoint | no | min frontier, plan input |
| `.../plans/<plan_id>.json` | restore plan | no | target T, base, segments |
| `.../reports/<id>.json` | restore/verify report | no | timings, hashes, verdict |
| `.../leases/<target_id>.json` | restore lease | TTL | one restorer |

Names are immutable once written. `current.json` is the only mutable object
and is replaced by a new generation, never edited in place.

### 4.2 Encoding rules

- Manifests: canonical JSON (UTF-8, sorted keys, no floats, integers as
  decimal, byte strings base64) so a hash is reproducible. Unknown fields are
  rejected on read; optional fields have explicit defaults.
- Segments: binary header + records + footer; no JSON per entry; length-prefixed
  and checksummed.
- Versioning: every object has `format` and `version`. A reader refuses a major
  version it does not know; a writer never writes a version it cannot read.
- Timestamps: UTC RFC 3339 for human fields; TSOs are unsigned 64-bit decimal.

### 4.4 Indexing and lookup

- A restore to `T` first resolves `T` to a global checkpoint `G` with
  `G.checkpoint_ts >= T` (the **oldest** checkpoint that covers `T` is used for
  audit; the newest base below/equal `T` is selected).
- For each range, the checkpoint gives `archived_through_index` and the chain
  head. The plan lists segments to read; no object listing is required on the
  restore path, which avoids eventual-consistency and scale problems.
- Segment lookup by time uses the per-range `first_commit_ts`/`max_commit_ts`
  hints only as a filter; the replayer still scans the segment records and
  applies `commitTS <= T`. Because commitTS is **not** monotonic in Raft index,
  no binary search assumes order.
- Base chunk lookup uses the page index and range bounds; chunks are read in
  parallel by range/page.
- Meta lookup uses the meta checkpoint and meta state snapshot; range-map
  changes carry a TSO so the map at `T` is derivable. If a meta change lacks a
  TSO (legacy), the archiver records its observation TSO and flags the plan.

### 4.5 Checksums and integrity

| Layer | Mechanism | Purpose |
|---|---|---|
| Record | CRC32C over type/length/payload | detect torn/bit-flipped records cheaply |
| Segment | SHA-256 over the complete sealed bytes | object integrity |
| Chain | `prev_segment_sha256` per range | detect gaps, reordering, truncation |
| Base chunk | SHA-256 per chunk (existing) | integrity, range containment |
| Base page | SHA-256 per page | index integrity |
| Manifest | SHA-256 of canonical bytes | detect manifest edits |
| Global index | Merkle root over segment/page hashes | one root in the report |
| Authenticity | Ed25519/HMAC signature over checkpoints and timeline | detect tampering/rollback; checksums alone are not authentication |
| Anti-rollback | generation + previous hash + signed timeline | a stale but valid checkpoint cannot be substituted silently |

Verification happens: after upload (read-back/hash), before a checkpoint is
published, during restore (streaming), during GC (before delete), and in a
nightly verify job (sample + full scan on rotation). A failure quarantines the
object, pages, and blocks checkpoints that reference it; it never repairs in
place.

### 4.6 Encryption and key management

- **Envelope encryption.** A KEK lives in KMS/HSM and never leaves it. A random
  256-bit DEK is generated per segment/base set; the DEK is wrapped by the KEK
  and stored in object metadata. Data is AES-256-GCM with streaming frames
  (e.g. 1 MiB), each frame authenticated; the final tag covers the object.
- **AAD binds identity:** `cluster_id | incarnation | range_id | start_index |
  end_index | format_version | key_id`. A segment moved to another range or
  index fails authentication.
- **Nonces:** random 96-bit per object plus a per-frame counter; a DEK is never
  reused for two objects with overlapping nonce spaces. Per-segment DEKs make
  nonce-collision risk negligible even at scale.
- **Manifests** are signed; sensitive fields may be encrypted. Object names
  reveal only ids, index ranges and timestamps — document this leakage. If the
  threat model requires hiding topology, encrypt the manifest body and keep a
  minimal plaintext header.
- **Rotation:** KEK rotation re-wraps DEKs (no data rewrite); DEK rotation per
  base generation; old keys stay available for the retention window and are
  then destroyed. Crypto-shred: destroying the wrapped DEK/KEK makes the data
  unreadable; deletion is not sufficient alone.
- **Availability:** a KMS outage blocks restore; an offline escrow (split
  knowledge, HSM-backed) is required for disaster recovery. Tested quarterly.
- **Transport:** TLS 1.3/mTLS between agents and object store/KMS; no static
  long-lived secrets in configs; workload identity/instance roles; least
  privilege (restore credentials are read-only).

### 4.7 Retention and GC

- Retention target: 7 days. The **restorable window** is
  `[oldest_restorable_ts, latest_checkpoint_ts]`.
- GC is dependency-aware, not age-only:
  1. Build the live set: for each base that can serve a `T` in the retained
     window, its chunks/pages/manifest; for each range, segments referenced by
     a checkpoint at or after that base's `T_base`.
  2. Add a grace period (e.g. 24 h) and any restore lease pins.
  3. Mark-and-sweep in dependency order: never delete a segment referenced by a
     live checkpoint; never delete the last complete base; never delete a base
     whose `T_base` is the only lower bound for a retained point.
  4. Delete objects only after a dry-run report and a second confirmation;
     object versioning/Object Lock provides a backstop.
- Clock: use a trusted coordinator clock and object-store `Last-Modified` as a
  cross-check; never use a node's local clock as the only ageing source.
- Deletion order: unreferenced segments first, then pages, then manifest, then
  base record; the timeline pointer is updated last. A crash mid-GC leaves
  unreferenced objects (safe) and a resumable job.
- `oldest_restorable_ts` is recomputed after GC; if it becomes newer than
  `now - 7d + safety`, GC refuses and pages (it would violate the window).
- Legal hold: a hold pins a base/point; GC respects it and never silently
  shortens the window.
- Audit: every delete and hold is recorded with operator, plan, object hashes.

### 4.8 Upload atomicity

- **Immutable objects.** Data objects are never overwritten. A retry produces
  the same bytes and the same key (idempotent) or a new generation.
- **Multipart.** Segment/chunk upload uses multipart with per-part checksums and
  a full-object checksum; the object is visible only after `CompleteMultipart`.
  A partial upload is unreferenced and cleaned by the orphan job.
- **Ordering.** Per range: seal segment locally (fsync) → upload data →
  upload meta → verify read-back → write `range checkpoint`. Per cluster:
  after all ranges, write the global checkpoint → update timeline `current`.
  A checkpoint never references an object that was not verified.
- **Pointer update.** `current.json` is replaced with `If-Match` on the previous
  generation (or a versioned bucket); if the store lacks CAS, write a new
  generation object and then a small pointer, and have readers pick the highest
  valid signed generation. A stale pointer is safe (older restore point) and is
  alerted; a pointer to a missing object is impossible because it is written
  last.
- **Single writer.** One archive epoch per range (leader term/incarnation); a
  lower epoch is rejected by the checkpoint. A second writer is a split-brain
  alarm, not a merge.
- **Read-back.** After upload, read the first/last bytes and the stored
  checksum; full verify is asynchronous but must pass before the object is
  eligible for a checkpoint (for large segments, verify the stream hash during
  upload and confirm the store's checksum).
- **Failure response.** Retry with exponential backoff and jitter; fail the
  range checkpoint, not the cluster; if the object store is down, the
  truncation gate keeps the log (disk pressure is handled in §6).

### 4.9 Versioning and compatibility

- `format_version` is per object family. Readers support the current and the
  previous major version for one release cycle; a restore plan records the
  versions it read.
- A newer writer must not produce objects that an older reader would silently
  misinterpret; unknown critical fields force a hard error.
- Existing `distributed-db-kvbackup` format v1 remains readable as a base for
  full restore; it is not a PITR archive. A future base v2 can be wrapped in the
  PITR timeline without changing chunk semantics.

### 4.10 Capacity and object counts (1 TB design point)

| Item | Assumption | Count/size |
|---|---|---|
| Base, 1 TB logical | 64 MiB chunks | ~16k chunks |
| Base pages | 1,000 chunks/page | ~16 pages |
| Base compressed | 0.45× | ~450 GB |
| Daily change | 10% of dataset | ~100 GB logical |
| Daily log, compressed | 0.5× | ~50 GB |
| 7-day logs | 7 × 50 GB | ~350 GB |
| 8 daily bases | 8 × 450 GB | ~3.6 TB |
| Total retained | bases + logs | ~4 TB |
| Log segments/week | 64 MiB | ~5.5k |

Eight bases, not seven: the oldest restorable point in a 7-day window needs a
base at or before `now - 7d`, so one base older than the window start must be
kept as the anchor. The 8th is also the safety margin for a failed base job.

The current 1 MiB / 1000-key chunking would produce ~1M chunks and a flat
manifest of hundreds of MB; base v2 must use larger chunks and paged indexes
(§4.3). Object-store request cost is dominated by PUT/GET counts, not bytes;
16k chunks is two orders of magnitude cheaper than 1M.

## 5. Restore flow into an isolated cluster

### 5.1 Inputs and preconditions

- Target `T` (TSO or wall clock) and an optional target topology.
- A global checkpoint covering `T`; a complete base with `T_base <= T`; all
  range segments needed for `(T_base, T]`; a meta state at/through `T`.
- The source cluster is either lost or fenced read-only. Never start a restore
  against a live, writable source.
- The target cluster is new/empty and has no client listeners, no scheduler, no
  GC, no auto-split, no archive, and no shared credentials with the source.
- Capacity check: base + replay staging + free space for the final store,
  plus 20% headroom.
- A restore lease in the object store; a plan hash approved by an operator
  (two-person rule for production).

### 5.2 Phases

| Phase | Action | Verification | If it fails |
|---|---|---|---|
| 0. Plan | resolve `T`, select base/checkpoint, list segments, estimate RTO, print first included/excluded commitTS | object existence + hashes from checkpoint; capacity | refuse; no writes |
| 1. Fence | freeze source; create target incarnation; acquire restore lease | source read-only/dead; no other restorer; epoch set | abort; source untouched |
| 2. Provision | new cluster id/epoch, certs, empty store, meta at `T`, TSO high-water, target range map, restore mode | target rejects client RPCs; TSO > max commit; map contiguous | tear down target |
| 3. Base | download chunks in parallel, verify, import at `base_ts`, route by target range | every chunk hash/bounds/order; totals | retry chunk; never skip |
| 4. Replay | read segments in lineage/index order, filter by `commitTS`, apply commands, stage prewrites | per-range progress checkpoint; no gaps; idempotent | resume from last verified index |
| 5. Resolve | resolve every remaining lock and staged overlap prewrite through its primary | zero orphans; counts recorded | fail and investigate; never cut over |
| 6. Verify | structural, digest, sampled logical, SQL/index, TSO, isolation | all checks pass; report signed | fail; target remains sealed |
| 7. Cutover | commit epoch/cutover in meta, enable clients, update discovery/credentials, smoke | old clients rejected; smoke reads/writes | roll back before client writes; otherwise incident |
| 8. Seal | seal old timeline, start archive for new incarnation, run post-cutover verify | new archive checkpoint advances | page |

### 5.3 Fencing, epoch and isolation

- **Cluster incarnation/epoch.** Each cluster lifetime has a UUID and a
  monotonic `incarnation` number stored in meta and presented by clients. A
  restore target gets `incarnation = old + 1` (or a new UUID plus a higher
  number). Meta and clients reject a request from a lower incarnation. This is
  distinct from the per-range `Version`/epoch
  ([`internal/meta/meta.go`](../../internal/meta/meta.go),
  [`internal/kvserver/range_host.go`](../../internal/kvserver/range_host.go)),
  which fences stale range maps; both are used.
- **Source fencing.** Preferred: stop the source cluster. If it is partially
  alive, network-isolate it and remove its credentials; if neither is possible,
  do **not** cut over — a split-brain write after cutover would be
  unrecoverable without another restore. Automatic fencing via a lease service
  is future work; the runbook is explicit about the manual step.
- **Restore target isolation.** No external listeners; only internal import and
  verify RPCs authenticated with a restore token; separate KMS/object-store
  read-only credentials; separate certificates; no route from clients; no
  scheduler or auto-merge; GC/archive disabled; metrics allowed.
- **Restore lease.** A TTL lease keyed by target id prevents two restorers from
  writing the same target. The lease is renewed; expiry requires operator
  action to resume, never automatic takeover.
- **Atomic cutover.** Cutover is a single meta commit
  `{old_incarnation, new_incarnation, T, plan_hash}` plus enabling client
  listeners and updating discovery. Before it, the source is authoritative;
  after it, the target is. There is no dual-write and no client-visible
  intermediate state. If the process dies between meta commit and listener
  enable, the target is authoritative but unreachable; the runbook completes
  the enablement or fences the target and re-enables the source (which has not
  accepted writes because it was fenced).

### 5.4 Target range map and TSO

- The target map can be:
  - the archived map at `T` (same split points, new range ids/replicas), or
  - a fresh contiguous map chosen by the restore tool (recommended default for
    a new cluster: same number of ranges as the source, split points sampled
    from the base), or
  - a single range for small datasets.
- Replay is by user key, so the map is not a correctness dependency. It is a
  serving/placement decision. If the archived meta is unavailable, a fresh map
  allows data recovery but the report marks `topology=reconstructed` and
  requires approval.
- TSO: `LastTS = max(T, maxCommitTSInBaseAndReplay, archivedMetaLastTS) +
  margin`; derive physical/logical; persist through meta Raft before enabling
  clients. Verify `maxCommitTS < LastTS`.
- Base import writes each key's value at `base_ts = T_base` (a reserved TSO
  that no transaction used). A replay commit at `commitTS > T_base` writes the
  newer version; a delete writes a tombstone. A base value is never written at
  a synthetic timestamp newer than `T_base`.

### 5.5 Replay rules

The replayer parses committed segments, not raw WAL bytes, and applies the
**semantics** of each command to the target MVCC store. It ignores range
placement, so splits/merges do not change the result.

| Command | Condition | Action |
|---|---|---|
| `noop`, membership, `split_prepare`, `merge_prepare` | always | skip; record lineage; no user-visible change |
| `prewrite` | `T_base < startTS <= T` | apply the lock and provisional data immediately; its commit is in the window or is resolved afterwards |
| `prewrite` | `T_base - Δ_overlap <= startTS <= T_base` | **stage only** (key, value, primary); do not create a lock. Staged entries are resolved against the primary at the end (§3.7): commit if the primary committed at `c <= T`, otherwise discard — the base already reflects every commit at or below `T_base`. |
| `prewrite` | `startTS < T_base - Δ_overlap` | not replayed; a later commit referencing it is `ErrMissingPrewrite` (§5.5 overlap) |
| `prewrite` | `startTS > T` | skip (transaction starts after the snapshot) |
| `commit` | `commitTS <= T_base` | skip (base already reflects it; do not recreate a lock) |
| `commit` | `T_base < commitTS <= T` | apply from the target lock or from a staged prewrite; if neither exists, abort with `ErrMissingPrewrite` |
| `commit` | `commitTS > T` | skip; leave the lock/stage for resolution |
| `rollback` | `startTS <= T_base` | skip (base reflects the rollback); discard any staged prewrite |
| `rollback` | `T_base < startTS <= T` | apply (removes the lock or discards the stage) |
| `prewrite_commit` | expand: commit part `<= T_base` skip; `(T_base, T]` apply; `> T` skip | 1PC; self-contained; no lock to resolve |
| `txn_batch` | expand each sub-command with the same rules | per-command outcomes are not replicated; apply the successful ones |
| unknown command type | always | **hard failure**; do not silently skip user data |

Replay is **not a client retry**. It must use an import path that trusts the
archived commit: it writes data/write records at the recorded `commitTS` and
does not re-run `prewrite` conflict detection. Running the normal client
`Prewrite`/`Commit` path would reject a valid history (out-of-order deliveries,
already-resolved locks, a lock whose primary is in a predecessor range) and
would allocate fresh timestamps, which defeats point-in-time recovery. The
import path must still validate record structure and checksums; it bypasses
only concurrency/conflict checks that the source already enforced.

Ordering:

- Process ranges in **lineage order** (predecessors before successors), each
  range in Raft-index order. This preserves per-key order when a split/merge
  moves a key.
- The prewrite staging area is **global to the restore**, keyed by
  `(startTS, userKey)`, not per range: a commit in a successor range must be
  able to materialise a prewrite staged from a predecessor range. At the end of
  replay, anything still staged is discarded (it is not committed at `T`).
- Within a range, prewrite precedes its commit; a commit for a key whose
  prewrite is in a predecessor range is processed after that predecessor.
- If lineage is unavailable or a commit's lock is missing outside the replay
  overlap, fall back to a **two-pass staged replay**: pass 1 stages prewrites
  keyed by `(startTS, userKey)`, pass 2 applies commits/rollbacks and discards
  uncommitted staged entries. The fallback is slower and uses disk; it is the
  safety net, not the default.
- Replay is idempotent: repeating a segment rewrites the same version keys and
  lock operations. Progress is checkpointed per range (`last_applied_index`);
  resume skips already-applied segments after verifying their hashes.

**Base-covered prewrites.** A prewrite at or below `T_base` is not applied as a
lock by default. Such a transaction either committed at or below `T_base` (the
base already contains the outcome, and its per-`commitTS` write record is
intentionally not reproduced) or commits after `T_base` (its values are needed).
Replaying it as a lock would create a lock whose primary commit record exists
only as a base value at `base_ts`, and the resolver would misclassify it. The
replayer therefore stages prewrites in the overlap `[T_base - Δ_overlap,
T_base]` and resolves each staged entry against its primary at the end: if the
primary committed at `c <= T`, the staged key is committed at `c`; otherwise it
is discarded. This is also why the base is exact at `T_base`: the barrier
waited for those transactions to resolve.

**Overlap before `T_base`.** A transaction may prewrite before `T_base` and
commit after it. The base does not contain it (it was not visible at `T_base`),
so its prewrite values must come from the archive. The replay window therefore
starts at `T_base - Δ_overlap`, with `Δ_overlap >= Δ_txn_max + max_clock_skew`.
Logs are retained for at least the retention window plus this overlap. A
commit in `(T_base, T]` whose prewrite is older than the retained overlap is a
restore failure (`ErrMissingPrewrite`), not a silent data loss; the plan
preflights this by checking the oldest segment index against the commit's
`startTS`.

### 5.6 Verification

| Check | What it proves | Required |
|---|---|---|
| Object hashes, chain, manifest signatures | archive integrity/authenticity | yes |
| Base totals, chunk bounds/order | base complete and in-range | yes |
| Range/replay coverage: every segment gap-free through `T` | no missing changes | yes |
| No locks remain; zero unexplained orphans | transactions resolved | yes |
| Every write record has a data record (put) or is delete/rollback | MVCC structural integrity | yes |
| `maxCommitTS < LastTS` and TSO monotonic | future writes visible | yes |
| Sampled point reads at `T` vs replay ledger | semantic spot check | yes |
| Full sorted `(key,value)` digest vs an independent model (drill) | full semantic equality | drills/tests |
| SQL: catalog, row, index, unique-marker, sequence consistency | SQL layer valid | yes |
| Range map contiguous, covers keyspace, replicas placed | target can serve | yes |
| No client accepted during restore | isolation | yes |

The full digest in a production drill is computed by a second, independent
restore run or by a reference model; it is optional for an emergency restore
because it doubles RTO. The sampled check and structural checks are mandatory.

### 5.7 Cutover and rollback

1. Freeze source (if not already dead) and confirm no writes.
2. Commit `Cutover{old, new, T, plan_hash}` to the target meta (Raft).
3. Enable target client listeners and TSO allocation; update service
   discovery/DNS/credentials; revoke old credentials.
4. Smoke: read known keys at `T`, write a probe key, read it back at the new
   TSO, check archive checkpoint advances.
5. Seal the old timeline (`state=sealed`), start the new incarnation's archive,
   record the report.

Rollback:

- Before step 3: discard the target; source is untouched.
- After step 3 but before any client write: fence the target, re-enable the
  source (it was fenced and has no new writes). This is the only safe rollback
  window.
- After a client write to the target: no rollback; perform another PITR to a
  later point if needed. Treat as an incident; preserve the report.

### 5.8 Post-cutover

- The new archive timeline starts at the new incarnation; the old timeline is
  sealed and retained for the old window, then GC'd.
- Run a post-cutover verify (sample + structural) and a backup base as soon as
  practical; the first new base should not wait 24 h if the restored base is
  already old.
- Record RPO/RTO evidence: `T`, first included/last excluded commit, phase
  timings, bytes, object counts, verification results, operator approvals.

Detailed notes on the six required failures:

**Upload gap.** The source log is the buffer: the truncation gate refuses to
remove entries above `archived_through_index`. A gap therefore costs local disk
and shrinks the *advertised* window, but not RPO in strict mode (commits wait;
they fail rather than ack). At 80% log disk the system fails writes closed and
pages; it never silently drops the tail or truncates unarchived entries. If the
operator explicitly switches to relaxed mode, the window and RPO both degrade
and the event is recorded in the timeline.

**Partial archive.** Because only a verified segment gets a range checkpoint,
and only range checkpoints get a global checkpoint, a partial upload is
invisible to readers. The orphan cleaner removes unreferenced objects after a
grace period. Resume re-uploads from the last checkpoint; duplicate bytes are
idempotent.

**Clock/TSO skew.** TSO never goes backwards within an incarnation because
`AllocTS` uses `max(now, lastTS)` and the high-water is replicated
([`tso.go:25-60`](../../internal/meta/tso.go#L25-L60)). A forward jump creates a
gap (harmless to TSO order but shifts wall-clock mapping); a backward jump is
clamped. Restore sets `LastTS` above every restored commit; if the target clock
is behind, the allocator still moves forward. The commit lease bounds the
"allocated long before proposed" anomaly. A meta leader change is safe because
the new leader loads `LastTS` from replicated state; the archiver records the
incarnation and rejects mixed streams.

**Range split/merge during backup.** The base aborts on a range-map change and
retries; the log archive follows child ranges and records lineage. Replay is
logical and uses lineage order, so a key that moves is not lost or duplicated.
The dangerous case is a child range created but not registered with the
archiver before its log is truncated; the truncation gate blocks because the
child has no archive checkpoint. This is a page, not a silent hole.

**Compaction deleting needed log.** Every prefix truncation path is gated:
local snapshot creation ([`internal/raft/node.go:618`](../../internal/raft/node.go#L618)),
snapshot install ([`node.go:881`](../../internal/raft/node.go#L881)), and
chunked install ([`node.go:1021`](../../internal/raft/node.go#L1021)) converge
on `FileStore.TruncatePrefix`
([`internal/raft/filestore.go:419-440`](../../internal/raft/filestore.go#L419-L440)).
The store clamps the requested index to `min(requested, archived_through)` and
reports a blocked count. Divergent-suffix `Truncate` is unaffected because it
removes uncommitted entries that were never archived. A store that does not
implement the gate cannot be used for PITR; it is a startup check, not a
runtime hope.

**Restore interrupted.** The target is sealed and not addressable by clients;
no partial state is exposed. The restore report and per-range progress are
written after each verified segment/base page. Resume re-verifies hashes and
continues; a target that cannot be proven consistent is discarded, not
patched. If interruption happens after cutover, it is an incident: the target
is authoritative, the source is fenced, and the recovery is another restore to
a later `T` (never "resume" a cut-over cluster from the old plan).

## 7. RPO/RTO math and monitoring

### 7.1 RPO model

**Strict mode (required for the stated RPO 0).** The commit acknowledgement
sequence is:

1. client commit RPC → leader proposes the commit entry;
2. entry is fsynced on a Raft quorum and applied;
3. the range archive agent seals/upload the segment containing the entry;
4. the range checkpoint is updated to include it (verified object);
5. only then is the client acknowledged.

If any step fails, the client gets an error/unknown and retries idempotently at
the same `commitTS`. If step 5 happened, steps 1–4 happened, so the commit is
in a verified checkpoint. A post-loss recovery that takes the union of per-range
checkpoints (and resolves locks) contains every acknowledged commit. This is
the RPO 0 proof; the price is one archive round trip on the commit path and a
CP failure mode when the archive is unavailable.

To avoid one object per commit, acknowledgements waiting on strict mode are
**coalesced** for `Δ_coalesce` (5–25 ms) or up to a size/entry cap; one segment
and one checkpoint serve the whole group. Strict ack latency is therefore
`Δ_coalesce + upload + checkpoint`, and the group is never acknowledged before
every member is covered. The cap bounds the ack wait; the coalescing factor
bounds object count.

**Relaxed mode (not compliant).** The client is acknowledged after step 2;
archive runs asynchronously. For F2 (total primary loss), an acknowledged
commit can be lost if it was not uploaded:

`RPO_relaxed ≈ L_upload = t_seal + t_upload + t_checkpoint + t_detect`

Measured at p99. Target `<= 60 s` is achievable, but it is **not 0**. The
timeline and reports mark the mode; an operator cannot enable relaxed mode
silently.

**RPO 0 is not "zero data loss for every possible `T`".** It means the
recovery point (latest recoverable, or an advertised `T` at/after the commit)
contains all acknowledged commits. Restoring to an earlier `T` intentionally
drops later commits (that is the point of PITR and must be confirmed).

**Recovery point vs advertised point.** `checkpoint_ts` is conservative: a
long-lived lock can hold it below a newer, already-archived commit. For
disaster recovery, `latest_recoverable` uses the union of complete per-range
checkpoints and resolves locks; it can include commits above the advertised
`checkpoint_ts`. The UI shows both; a live restore uses only `checkpoint_ts`.
If this distinction is not implemented, a long lock can make the advertised
window lag and an operator might restore to a point that excludes an
acknowledged commit — a false RPO 0 claim, not a data loss in the archive.

### 7.2 RTO model

Define:

- `D`: logical dataset bytes (1 TB).
- `C`: compressed base bytes (`0.45 D` planning).
- `B_down`: aggregate download bandwidth (object store → restore nodes).
- `B_import`: aggregate import bandwidth (decode + MVCC write).
- `Δ`: change bytes in the replay window (`change_rate × D × hours/24`).
- `B_replay`: aggregate replay bandwidth (parse/apply).
- `T_base = max(C/B_down, D/B_import)`.
- `T_replay = Δ/B_replay`.
- `T_verify`: sampled/structural verification (2–3 min); full digest is extra.
- `T_fixed = T_decide + T_provision + T_resolve + T_cutover + T_smoke`.

`RTO = T_fixed + T_base + T_replay + T_verify`.

Worked example (1 TB, 24 h base, 10%/day change, 5 restore nodes, 2 GB/s
download, 2 GB/s import, 400 MB/s replay):

| Phase | Budget |
|---|---|
| decide + approvals | 5 min |
| provision target | 2 min |
| base (`max(450/2, 1000/2)` GB/s ≈ 8.3 min) | 8.3 min |
| replay (100 GB / 400 MB/s) | 4.2 min |
| lock resolution | 1 min |
| verify (sampled + structural) | 2 min |
| cutover + smoke | 3 min |
| **p50 total** | **25.5 min** |
| p99 (1.2× base/replay) | ~29–31 min (borderline) |

To make p99 comfortably < 30 min, at least one of:

- base interval 6–12 h (replay <= 50 GB → ~2 min), or
- ≥ 5 restore workers at ≥ 2.5 GB/s aggregate import, or
- incremental/physical base that cuts `T_base` (future).

Sensitivity:

| Dataset | Base interval | Import BW | Replay BW | p50 RTO | p99 verdict |
|---|---|---|---|---|---|
| 1 TB | 24 h | 2 GB/s | 400 MB/s | 25.5 min | borderline |
| 1 TB | 24 h | 2.5 GB/s | 400 MB/s | 24 min | pass (~27 min p99) |
| 1 TB | 12 h | 2 GB/s | 400 MB/s | 23 min | pass |
| 1 TB | 6 h | 2 GB/s | 400 MB/s | 22 min | pass |
| 1 TB | 24 h | 1 GB/s | 200 MB/s | 38 min | fail |
| 2 TB | 12 h | 2 GB/s | 400 MB/s | 34 min | fail (need 4 GB/s or incremental) |

Consequence: "RTO < 30 min at 1 TB" is a **configuration-dependent claim**, not a
property of the code. The sprint gate must specify the base interval and
throughput; otherwise the claim is untestable. The test plan (§8.5) pins them.

### 7.3 Storage and bandwidth budget

- Base: 450 GB compressed/day × 8 = 3.6 TB (daily full, including the anchor
  base older than the window), plus 350 GB logs = ~4 TB. A 6–12 h **incremental**
  base reduces replay time without doubling storage; 12 h *full* bases would
  double base storage to ~7 TB. v1 starts with daily full + 7 days logs.
- Archive write bandwidth: 50 GB/day average ≈ 0.6 MB/s; peak (bulk load) can
  be 10–50×; segment buffering and backpressure handle it.
- Restore read bandwidth: burst 2–3 GB/s for the base; object store request
  rate ~16k chunks + ~5k segments, well within limits.
- Commit overhead strict: one on-demand seal + upload + checkpoint round trip
  per commit batch (or a short timer); p50 +20–40 ms, p99 +80–150 ms on
  same-region S3. If unacceptable, the requirement must change to relaxed
  (RPO > 0) or an archive relay must be introduced (future work).

### 7.4 Restorable window

- `oldest_restorable_ts = max(oldest complete base T_base, now - 7d + safety)`.
- `latest_restorable_ts = checkpoint_ts`.
- Window = `latest - oldest`; alert if < 6.5 days.
- A restore plan outside the window is refused; it never silently clamps.

## 8. Test plan

### 8.1 Principles

- Test the **contract**: state at `T`, not internal call sequences.
- Deterministic seeds and a time source that can be stepped; no sleeps for
  correctness, only for timing bounds.
- An **independent oracle**: a workload generator records `(startTS, commitTS,
  mutations, outcome)` and computes the expected state at `T` without using the
  restore code.
- Inject failure at every phase boundary, not only at the end.
- Every test runs in strict and relaxed modes where applicable; strict must
  prove RPO 0.

### 8.2 Test matrix

| ID | Level | Scenario | Assertion |
|---|---|---|---|
| T-01 | unit | segment encode/decode, CRC, hash chain, manifest canonicalization | byte-identical round trip; corruption detected |
| T-02 | unit | replay filter at `T_base`, `T`, commit boundaries | precise include/exclude; no off-by-one |
| T-03 | unit | lock resolution cases (primary committed/rolled back/missing) | correct commit/rollback; no orphans |
| T-04 | unit | encryption round trip, AAD swap, wrong key, tamper | fail closed; no plaintext |
| T-05 | integration | base barrier: lock at `T_base`, late commit, 1PC apply lag | base never misses a commit <= `T_base` |
| T-06 | integration | random `T` over a workload with deletes, overwrites, cross-range 2PC, rollbacks | full key-by-key equality with oracle |
| T-07 | integration | split/merge during base, during replay, key moved between prewrite/commit | no loss/duplication; lineage order |
| T-08 | integration | partial commit at source (primary committed, secondary lock) | secondary committed at primary's ts |
| T-09 | chaos | kill archiver at every phase (seal/upload/meta/checkpoint/pointer) | no checkpoint references corrupt/missing object; resume |
| T-10 | chaos | kill base builder at chunk/manifest/upload | base is all-or-nothing; retry |
| T-11 | chaos | kill restore at base/replay/resolve/verify/cutover | target sealed; resume or discard; no partial serving |
| T-12 | chaos | object store 5xx/timeout, network partition, disk full, KMS outage | backpressure/fail-closed; no silent loss |
| T-13 | chaos | clock skew/step on meta leader; target clock behind | TSO monotonic; wall mapping reported; no regression |
| T-14 | chaos | GC race with restore, stale checkpoint, concurrent restores | leases/pins prevent deletion/dual write |
| T-15 | scale | 1 TB, 7 days logs, 10%/day churn, 5 nodes | p99 RTO < 30 min; window >= 6.9 d; no OOM |
| T-16 | consistency | full scan after restore: locks, write/data, tombstones, TSO, range map | zero defects |
| T-17 | SQL | catalog/rows/indexes/unique/sequences after restore; DDL in window | SQL-level consistency |
| T-18 | security | revoked creds, wrong mTLS, unauthorized KMS, old client epoch | access denied; old clients fenced |
| T-19 | perf | archive overhead on commit p50/p99; strict vs relaxed | within budget; report |
| T-20 | drill | monthly automated full drill + signed report | RPO/RTO evidence; G3 sign-off |

### 8.3 Random point-in-time tests

- Generate 10k transactions over 1–10 ranges with: puts, overwrites, deletes,
  cross-range 2PC, 1PC, rollbacks, lock timeouts, splits, merges, and a few
  long transactions (bounded).
- Record each txn's `startTS`, `commitTS`, mutations and outcome; compute
  `state(T)` for 1,000 random `T` (plus boundary cases: exactly a commitTS,
  exactly `T_base`, just before/after a split, mid-transaction, before the first
  base, after the checkpoint).
- Restore each `T`; compare every key/value and key absence; compare a sorted
  digest; report the first difference with txn provenance.
- Expect: exact equality for every `T <= checkpoint`; refusal for `T` outside
  the window; a plan that prints the boundary.
- Boundary tests are mandatory: a `T` equal to a commitTS includes it; `T - 1`
  excludes it; a delete at `T` is a tombstone (key absent), not an old value.

### 8.4 Kill matrix

| Target | Kill points | Required outcome |
|---|---|---|
| Archiver | after read, after seal, mid-multipart, after upload, after meta, after range checkpoint, after global checkpoint, after pointer | old checkpoint remains valid; no missing reference; resume from last verified |
| Base builder | mid-chunk, after chunks, after manifest, mid-upload, after pointer | base invisible until complete; retry; no partial base |
| Restore | after plan, 50% base, 50% replay, during resolution, during verify, during cutover | target sealed; resume/discard; no client exposure; cutover atomic |
| Raft/meta | kill leader/follower during archive; meta leader change | no mixed incarnation; checkpoint monotonic; TSO monotonic |
| Node/disk | kill -9 KB server with unarchived tail; fill disk | gate blocks truncation; strict writes fail closed; no acked loss |
| Object store | 5xx, timeout, slow, read-only | retry/backpressure; no checkpoint on unverified data |
| KMS | deny/rotate during restore | restore fails closed; no plaintext fallback |

Each kill test asserts: (a) no checkpoint references an object that fails
verification; (b) a restore to the last checkpoint succeeds; (c) in strict mode,
zero acknowledged commits are missing; (d) the target was never client-visible
before cutover.

### 8.5 1 TB scale test

- 5 nodes, 3 AZ, 1 TB logical (1 KB average values), 1B keys or equivalent,
  realistic range count.
- Workload: 10%/day churn (updates/deletes, cross-range), 7 days of logs;
  daily bases; one node failure during the run.
- Measure: base build time/bytes, upload throughput, archive lag p99, unarchived
  bytes, checkpoint lag, restore phase timings, peak memory/disk, commit p99
  strict overhead, storage amplification, object counts/request counts.
- Pass: restore p99 < 30 min with the declared base interval/throughput;
  restorable window >= 6.9 days; zero verification failures; no OOM; no silent
  loss; strict RPO 0 in kill tests. Repeat with object-store throttling and a
  restore worker failure.
- Report: which phase dominates; if base dominates, test a 12 h/6 h base and
  an incremental base; if replay dominates, test a shorter base interval.

### 8.6 Consistency checks (run after every restore)

- Full key scan at `T`: every expected key present with the expected value;
  every unexpected key absent (including stale keys from a non-empty target).
- No locks; every write record has data (put) or is delete/rollback; no data
  version without a write record except invisible provisional data from a
  rolled-back prewrite (it is not visible and may be GC'd).
- `maxCommitTS < LastTS`; TSO monotonic; no duplicate version keys.
- Range map contiguous, covers the keyspace, replicas placed, target ranges
  host the data.
- Cross-range transactions: all-or-none at `T`; no partial commit.
- SQL: catalog tables, column definitions, indexes, unique markers, sequences,
  row counts; secondary index entry set equals table scan; no dangling index.
- Object-level: every base chunk/page hash, segment chain, manifest signature,
  global checkpoint signature.

### 8.7 Chaos and soak

- 72 h soak with continuous archive, GC, base, random `T` restores, node kills,
  object-store latency injection, clock steps, disk pressure.
- Ensure no goroutine/memory/disk leak; checkpoints keep advancing; window
  stays >= 6.9 d; GC does not delete live objects.
- Run a Jepsen-style partition test during archive and restore to confirm
  fencing/epoch; no two writers.

### 8.8 Security tests

- Encryption: ciphertext-only object store; wrong key/AAD fails; rotation
  re-wraps; crypto-shred makes data unreadable; no key material in logs.
- Access: restore credentials read-only; old client cert/epoch rejected;
  unauthorized KMS denied; audit entries for plan/restore/cutover/GC.
- Tamper: modify a segment/checkpoint; signature/hash detection; attempt to
  replay an old signed checkpoint; generation/anti-rollback rejects it.

### 8.9 Drills and acceptance

- Monthly automated drill: random `T` in the window, full restore into an
  isolated cluster, verify, cut over to a drill cluster, measure RTO, emit a
  signed report, destroy the drill cluster.
- Quarterly: key rotation/escrow test, full 1 TB restore, kill matrix subset.
- G3 exit: all §1.6 criteria pass; the report names the base interval,
  throughput, strict/relaxed mode, and any deviations.

## 9. Implementation slices and rough effort

Effort is in engineer-weeks (ew), rough order of magnitude for a team familiar
with the codebase. It excludes the code changes themselves (this ADR is
documentation only) and assumes the G1 durability work is already done.

| Slice | Scope | Effort | Depends on | Exit criteria |
|---|---|---|---|---|
| S0 | This ADR, threat model, decision review | 0.5 ew | — | approved |
| S1 | Prerequisites: commit lease/TSO safety; max txn lifetime; cluster incarnation/epoch; meta range-change timestamps; `FileStore` read cursor/export; truncation gate at `TruncatePrefix`; object-store client; metric scaffolding | 3–4 ew | G1 | gate blocks truncation in tests; commit lease enforced; epoch stored/rejected |
| S2 | Archive pipeline: segment format/seal, committed-only cursor, upload/verify, range checkpoint, meta archive, global checkpoint/safe point, base `T_base` barrier, paged base manifest v2, timeline | 4–5 ew | S1 | every committed entry archived; checkpoint advances; base is exact at `T_base`; truncation never exceeds archive |
| S3 | Restore: plan/preflight, base loader, replay (lineage/filter/staging), lock resolution, target provisioning, TSO high-water, restore mode/fencing/lease, cutover record, resume | 4–5 ew | S2 | random `T` restore into isolated cluster passes consistency; kill/resume works |
| S4 | Encryption/KMS: envelope keys, streaming AEAD, AAD, rotation, escrow, audit | 2–3 ew | S2 | no plaintext at rest; wrong key/AAD fail closed; rotation tested |
| S5 | Retention/GC: window computation, dependency live set, mark/sweep, grace/lease pins, Object Lock, dry-run/audit | 2–3 ew | S2 | 7-day window held; no live object deleted; GC race tests pass |
| S6 | Verification/ops: structural + SQL consistency checker, verify job, CLI (`plan/list/verify/restore/gc`), dashboards/alerts, runbooks, report signing | 2–3 ew | S3 | G3 drill report; alerts fire in fault injection |
| S7 | Scale/chaos/drills/security: 1 TB test, kill matrix, chaos soak, RTO tuning, pen-test of restore path, monthly drill automation | 3–4 ew | S3–S6 | 1 TB p99 < 30 min with declared config; RPO 0 evidence; drill passes |

**Total:** ~20.5–27.5 engineer-weeks for production-grade G3 (sum of the
midpoints, including S0). Critical path: S1 → S2 → S3 → S7 (S4/S5 can run in
parallel after S2; S6 after S3). The serial path is ~14–18 ew, so 3 engineers
do not compress it to a few weeks. Expect ~12–16 calendar weeks with 2
engineers and ~10–13 with 3.

**Minimum viable PITR (MVP), if schedule is tight:** the S1–S3 core
(prerequisites + archive + restore) ≈ **12–15 ew**, plus basic retention/verify
from S5/S6 (~2–3 ew) for a drillable system. It gives strict RPO 0,
point-in-time restore, and a verified isolated cutover, but not full encryption
(or only base encryption), SQL consistency checks, or the 1 TB p99 evidence.
Do not call G3 done without the 1 TB drill and encryption.

**Why the production plan's "4–6 weeks" is optimistic:** it predates the
archive API, commit lease, meta timestamps, cluster epoch, paged manifest,
restore replay/resolution, encryption, GC and 1 TB evidence. The 4–6 weeks may
cover a demo PITR on a small dataset; it does not cover the G3 acceptance
criteria.

### 9.2 Sequencing rules

1. Ship the truncation gate and commit lease **before** retaining logs for
   PITR; otherwise a snapshot/install can silently delete the tail.
2. Ship the paged base manifest **before** the first 1 TB base; the flat
   manifest is a known scalability failure.
3. Ship encryption **before** the first production restore; retrofitting keys
   over an existing archive requires a rewrite or dual-write period.
4. Ship GC **after** retention/window tests; a GC bug is irreversible.
5. Run a drill **before** declaring G3; a restore that was never drilled is a
   hypothesis.

### 9.3 Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Commit lease changes client semantics/latency | stalled transactions, SLO | batch/ack design; opt-in strict; monitor; document retry |
| Base scan load on live cluster | latency, long base | throttle; snapshot read; prefer 6–12 h incremental or physical base |
| 1 TB RTO misses p99 | gate failure | pin base interval/throughput; test early; incremental base |
| Lineage/replay bug | wrong restore | random `T` differential tests; hard-fail unknown commands |
| GC deletes a live object | PITR loss | dependency GC; dry-run; Object Lock; restore pins |
| KMS/object-store dependency | availability/RPO | fail-closed, escrow, optional second copy |
| Source fencing is manual | split brain | runbook; runbook test; future lease service |

## Consequences

**Positive.**

- PITR to any TSO in a 7-day window, with a mechanically checkable safe point.
- RPO 0 without a new primary write path; strict mode adds an archive
  persistence/acknowledgement step that copies the already-durable log entry to
  object storage.
- Restore is isolated and atomic at the cluster level; no more half-restored
  serving clusters.
- Reuses the existing logical base/verify code and remains layout-independent.
- Clear evidence trail for G3: checkpoints, hashes, drills, phase timings.

**Negative.**

- Strict mode couples commit availability and p99 latency to the archive and
  object store; a CP tradeoff that must be explicit with product.
- Operational complexity: archive agents, safe-point math, lineage, checkpoints,
  GC, keys, restore drills.
- Storage cost ~4 TB for a 1 TB dataset at 7 days with daily bases.
- RTO at 1 TB is throughput-bound and configuration-dependent; it is not a free
  property of the design.
- The base scan is a full read of the dataset; it must be throttled and
  scheduled.
- No tenant isolation in v1; a future multi-tenant product needs per-tenant
  keys, namespaces and restore authorization.

**Neutral.**

- Meta gains range-change timestamps, a TSO safety/lease mechanism, and a
  cluster incarnation. These are small protocol changes but must be rolled out
  before PITR.
- The existing logical backup format remains, extended with a paged manifest
  for scale.

## Open questions

1. **Is RPO 0 required for F2 (total primary-cluster loss), or only for F1
   (node/AZ loss)?** If only F1, relaxed mode is sufficient and avoids the
   commit-path latency/availability cost. This is a product decision with the
   largest impact on the design.
2. **Can the transaction protocol accept a commit lease and stale-commit
   rejection?** If not, a conservative safety lag is possible but the RPO 0
   proof weakens for pathological commit delays.
3. **Base interval and storage budget:** daily full (simple, ~4 TB) vs 6 h
   incremental (faster RTO, more complexity). The RTO gate needs a pinned
   choice.
4. **Exact topology restore vs reconstructed map:** default reconstructed map
   plus optional exact map, or exact map required for compliance?
5. **Object store and KMS choice:** S3 vs MinIO, Object Lock, cross-region copy,
   offline escrow ownership.
6. **Automatic source fencing:** lease service vs manual runbook. Manual is
   acceptable for a private single-tenant product but must be drilled.
7. **SQL DDL and schema version:** DDL is in the KV log, but a schema-version
   guard may be needed to refuse restoring a catalog that a newer binary cannot
   serve.
