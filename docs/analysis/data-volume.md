## 1. Из кода

- Ключ: 10-Б range-префикс + CF + key + 8 Б TS; write 10 Б; lock 22 Б + value
  (`internal/mvcc/mvcc.go`).
- Split: freeze → `StreamRange(1024)` → `ImportRecords` → `DeleteRange` **одним
  batch**; merge не удаляет префикс right (`kvserver/split.go`).
- `RangeStats` — полный обход префикса; `AutoSplit`/`AutoMerge` не вызываются
  из бинарей.
- MVCC GC реализован, но **вызовов вне тестов нет**; safe point не считается.
- Snapshot не периодический: WAL режется только снимком, replay — `os.ReadFile`,
  запись — JSON+base64 (`raft/filestore.go`).
- Backup: 1000 ключей/1 MiB, без сжатия, restore последовательный; `Scan` берёт
  все версии диапазона, `limit` — после.
- gRPC 16 MiB; meta: `AllocTS` — Raft-proposal на батч под `tsMu`, `SetRanges`
  пишет всю карту, WAL не тримится.

## 2. Overhead на ключ/значение (из кода)

| key / value | data+write | итого | overhead |
|---|---:|---:|---:|
| 16 / 64 Б | 99+45 | 144 | +80 % |
| 16 / 256 Б | 291+45 | 336 | +24 % |
| 16 / 1 КиБ | 1059+45 | 1104 | +6 % |

Короткие ключи дают доминирующие накладные; для 1 КиБ+ — лимит RPC (§8).

## 3. Disk amplification (оценка)

| Слой | Множитель |
|---|---:|
| live data+write | 1.0–1.3× |
| старые версии | 1×…N× — **GC не запускается** |
| lock + provisional | до 2× на время txn |
| Raft WAL | ≈1.37× записанного |
| compaction transient | 1.2–2× |
| RF=3 | ×3 по кластеру |

Append-only 1 ТБ по 256 Б → ≈4.5–8 ТБ диска. При перезаписях множитель не
ограничен (§4).

## 4. MVCC-версии и GC — риск №1

`versions ≈ N × (1 + u·D)`: 10⁸ ключей при 10 % перезаписей/день дают ×2 за
10 дней и ×11 за 100. Объём растёт от **записи**, а не от датасета. `GCWithStats`
для ТБ непригоден: полный скан и список удалений в RAM.

## 5. Range, split/merge, общий Pebble

3.1 млн ключей на ГБ (value 256 Б).

| Range | Copy (≈20–50 МБ/с) | Tombstone batch (≈) | Вердикт |
|---:|---:|---:|---|
| 256 МБ | 5–13 с | 30–60 МБ | рискованно |
| 1 ГБ | 20–50 с | 120–250 МБ | рискованно |
| 10 ГБ | 3–8 мин | 1.2–2.5 ГБ | нет |

Freeze держится всё копирование на всех репликах, копируются все записи, не
live-данные. `DeleteRange` собирает tombstone на запись в один batch: память и
время коммита линейны, лимита нет.

Один Pebble и memtable на узел: горячий range даёт stall на всех группах,
per-range квоты нет, а размер range нельзя взять из метрик Pebble — отсюда полный
скан в `RangeStats`; проход `AutoSplit` — O(датасет), 1 ТБ ≈2.8 ч.

## 6. Meta/TSO и число range'ей

- Каждая группа — Raft-node, WAL, таймеры, heartbeat 100 мс (30 в тестах) двум
  пирам: на узле ≈`(2/3)·R/T` RPC/с. 1000 range'ей → 6.7 тыс. RPC/с (22 тыс.
  при 30 мс), 11 тыс. → 73 тыс. (240 тыс.). Предел — сотни групп.
- TSO: 234 proposal/с при 30 тыс. ops/s — по силам, но каждый = fsync под
  `tsMu`; meta-WAL ≈20 МБ/сутки не тримится.
- `SetRanges` пишет всю карту (~80 Б/range): 11 тыс. range'ей ≈0.9 МБ на
  изменение, лог O(R²) до snapshot.

## 7. Secondary indexes (оценка)

Запись индекса: 19 Б MVCC + 21 Б префикса + value + PK + 10 Б write. Для
INT-ключа и 8-Б PK ≈110–130 Б на версию: один индекс ≈+1 запись в Raft и
+15–30 % диска на строку 300 Б; UPDATE такой колонки переписывает все индексы.

## 8. Backup, restore, WAL, крупные значения

| Объём | Backup (≈) | Restore (≈) |
|---:|---:|---:|
| 10 ГБ | 1–2 ч | 10–30 мин |
| 50 ГБ | 5–10 ч | 1–2 ч |
| 1 ТБ | 4–8 сут | — |

10 ГБ — рискованно, 50 ГБ — нет, 1 ТБ не бэкапится.

Backup квадратичен: на чанк вызывается `Scan(cur,end)`, читающий весь остаток
range'а, ≈K²/2000 декодирований. Размер ≈1.0–1.3× логики **без сжатия**.
Restore: 10⁶ чанков, verify читает всё, затем 10⁶ commit'ов по 10–20 мс.

WAL без автоснапшота растёт от всех записей; replay читает файл в RAM: 10 ГБ
записей → ≈13.7 ГБ RSS, 100 ГБ → OOM. Цель «<30 с на 100 ГБ» недостижима.

Значения: 16 MiB — потолок RPC, но value едет целиком в Get и Raft-entry
(JSON+base64), реальный предел ≈11–12 МБ. ≤1 МБ — комфортно, до 8 МБ —
рискованно, >12 МБ — нет.

## 9. Edgehash Bloom (отдельный продукт)

| Хешей | Bloom 1 % | Точные хеши |
|---:|---:|---:|
| 10⁹ | 1.2 ГБ | 32 ГБ |
| 10¹⁰ | 12 ГБ | 320 ГБ |

Bloom дёшев, точные хеши — ТБ. 65 536 сегментов — потолок 2-Б префикса; при 10⁹
это ~15 тыс. хешей на сегмент. Кэш ограничен `MaxCacheBytes`/`MaxSegments`.

## 11. 1 ТБ: нет

Диск выдержит (≈4.5–8 ТБ). Ломается процесс: нет GC; split ТБ-range = freeze на
минуты и tombstone-batch на сотни миллионов записей (OOM); авто-split сканирует
датасет; backup квадратичен; WAL реплеится в RAM; 73 тыс. heartbeat RPC/с на
узел неподъёмны. Для «рискованно» нужны GC, автоснапшоты, линейный backup,
split без freeze, лимит range'ей и placement.
